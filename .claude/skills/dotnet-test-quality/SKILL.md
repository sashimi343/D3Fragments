# D3Fragments のテスト品質

目的は「テストを増やす」ことではなく、「テストが検出できない不具合を減らす」こと。

## 合格ライン（`src/` のパッケージごとに判定）

| 指標 | ライン | 計測 |
|---|---|---|
| 分岐カバレッジ | 80% 以上 | dotnet-coverage + ReportGenerator |
| ミューテーションスコア | 70% 以上 | Stryker.NET + `scripts/StrykerSummary.cs`（除外前の値も併記する） |
| アサーションのないテスト・Skip・Sleep | 0 件 | `scripts/TestQualityCheck.cs` |
| テストのない public 型・診断 ID | 0 件 | 同上 |
| フレーキーなテスト | 0 件 | 全テストを 10 回実行 |

例外: `D3Fragments.Analyzers.CodeFixes` は残りが到達しないコードのため、基準未満（ミューテーション 68.4%、分岐 76.9%）を許容している。

## 計測

コマンドと Stryker の注意点は `dev-docs/for_library_maintainer.md` の「テスト品質の確認」に従う。補足:

- 時間のかかる処理（Stryker、繰り返し実行）はバックグラウンドで1つずつ実行する。並行するとタイムアウトの判定が狂う
- 静的チェックの指摘は名前ベースの推測なので、ソースを見て誤検知でないか確かめてから報告する
- フレーキー検出: Release ビルド後に `dotnet test D3Fragments.slnx -c Release --no-build` を 10 回実行し、1 回でも結果が変わったテストを報告する
- `D3Fragments.Testing.EFCore.Tests` は Docker が必要

## 手順

1. **範囲を合意する**: 対象のパッケージと、1回きりの診断か継続運用か。
2. **計測する**: ビルドと通常のテストが通ることを先に確認してから測る。
3. **生存ミュータントを分類する**: 本物の穴・等価・未計測・到達しないコードに分ける。基準と既知のパターンは [references/mutant-triage.md](references/mutant-triage.md)。「生存」を見て即テストを書かない。
4. **報告する**: パッケージ × 指標の表（合否付き）、本物の穴の一覧（優先度順）、除外した変異と理由、見つかったバグの疑い、ドキュメントとコードの食い違い。
5. **改善する**: 追加するケースをクラスごとに表で提案し、合意を得てから書く。パターンは [references/test-patterns.md](references/test-patterns.md)。
   - 固定してよい挙動は、ドキュメント（XML ドキュメントを含む）か既存のテストで裏付けがあるものだけ
   - 変異を入れても結果が変わらないテストは追加しない
   - ファイル整理が必要なら、追加より先に中身を変えない移動だけを行い、コミットを分ける
6. **再計測する**: 変更したパッケージを測り直す。届かなければ残りの内訳を示し、扱い（例外として認める、src を変える）をユーザーに決めてもらう。最後に全テストと静的チェックを1回通す。

## 守ること

- **`src/` は変更しない。** バグや仕様の曖昧さを見つけたら、直さずに報告する。
- テストの追加・コミットは、方針を説明して合意を得てから行う。
- Stryker の `ignore-methods` / `ignore-mutations` で除外しない（本物の変異まで消える）。等価ミュータントは `StrykerSummary.cs` で除外する。
