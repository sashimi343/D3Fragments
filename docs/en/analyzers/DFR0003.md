# DFR0003: Entity classes should not have public setters

| Property | Value |
|---|---|
| Rule ID | DFR0003 |
| Title | Entity classes should not have public setters |
| Default severity | Warning |
| Fix is breaking or non-breaking | Breaking |
| Code fix | Yes (properties only) |

## Cause

A class that directly or indirectly inherits the `D3Fragments.EntityBase<TId>` class declares one of the following members.

- A property that has a `set` accessor or an `init` accessor whose accessibility is `public`, `internal`, or `protected internal`
- A field whose accessibility is `public`, `internal`, or `protected internal` and that is not `readonly` (excluding `const`)

Note the following.

- If the accessor itself has no modifier, the accessibility of the accessor is that of the property.
- Accessors and fields that are `protected`, `private protected`, or `private` are not violations.
- The accessibility of the class itself (whether it is an `internal` class) does not matter.
- Properties that are explicit interface implementations are excluded.
- A violation is reported in the class that declares the member.

This rule is verified regardless of the architecture layer setting of the assembly (`ArchitectureLayerAttribute`).

## Rule description

The state of an entity should be changed through operations (methods).
If public setters are implemented, domain knowledge such as rules for state changes leaks outside the entity, and domain logic such as condition checks and value assignments is scattered across multiple places, which can reduce the maintainability of the code.

`init` accessors are also violations because object initializers allow arbitrary values to be set from outside the entity.
`internal` setters are also violations to prevent the state from being overwritten from other architecture layers in the same assembly.

## How to fix violations

Use operations (methods) instead of changing the state of the entity with public setters.
Change the accessibility of the setter to `private`. For fields, make them `private` or `readonly`.

The code fix changes the setter (`set` / `init`) of the property to `private set`.

## Example

```csharp
public class TodoItem : EntityBase<UuidV7>
{
    // Violates DFR0003
    public bool IsDone { get; set; }

    ...
}
```

```csharp
public class TodoItem : EntityBase<UuidV7>
{
    // Does not violate DFR0003
    public bool IsDone { get; private set; }

    public void Finish()
    {
        if (IsDone)
        {
            throw new DomainException(ErrorType.PreconditionFailed, "This item is already finished.");
        }
        IsDone = true;
    }
}
```

## When to suppress warnings

In general, do not suppress a warning from this rule.

## Suppress a warning

If you just want to suppress a single violation, add preprocessor directives to your source file to disable and then re-enable the rule.

```csharp
#pragma warning disable DFR0003
// The code that's violating the rule is on this line.
#pragma warning restore DFR0003
```

To disable the rule for a file, folder, or project, set its severity to `none` in the [configuration file](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files).

```ini
[*.cs]
dotnet_diagnostic.DFR0003.severity = none
```
