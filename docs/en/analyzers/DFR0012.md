# DFR0012: Do not save changes or control transactions outside pipeline behaviors

| Property | Value |
|---|---|
| Rule ID | DFR0012 |
| Title | Do not save changes or control transactions outside pipeline behaviors |
| Default severity | Warning |
| Fix is breaking or non-breaking | Non-breaking |
| Code fix | None |

## Cause

A method that saves changes or controls a transaction is called from a class whose module layer is not one of the following.
For details on module layer names and how module layers are determined, see [Module layers](../guide/01-architecture.md#module-layers).

- `Application_PipelineBehavior` (implementations of `IPipelineBehavior<TRequest, TResponse>`)
- `Infrastructure_DbContext` (classes derived from `DbContext`)
- `Infrastructure_UnitOfWork` (implementations of `IUnitOfWork`)

The following methods are checked.

| Type | Methods |
|---|---|
| `IUnitOfWork` (and its implementations) | All instance methods (`SaveChangesAsync`, `DiscardChanges`, `ExecuteInTransactionAsync`) |
| `DbContext` (and its derived classes) | `SaveChanges`, `SaveChangesAsync` |
| `DatabaseFacade` (`DbContext.Database`) | `BeginTransaction(Async)`, `CommitTransaction(Async)`, `RollbackTransaction(Async)` (including extension method overloads) |
| `IDbContextTransaction` | `Commit(Async)`, `Rollback(Async)` |

This rule is verified only when `ArchitectureLayerAttribute` is set on the calling assembly.

## Rule description

In D3Fragments, the pipeline behaviors (`UnitOfWorkBehavior` and `TransactionBehavior`) save changes and control transactions as a whole.
A request handler only needs to change aggregates, and does not need to be aware of whether to save or where the transaction boundaries are.

When a request handler or a repository saves changes or controls a transaction by itself, the following problems occur.

- The changes made so far are committed even when the handler ends with a business error (an exception).
- The transaction boundary defined by `ITransactionalCommand` and the timing of domain event delivery (before and after the commit) are broken.
- Saving is scattered across multiple places, and it becomes impossible to trace where changes are committed.

Classes derived from `DbContext` (for example, an override of `SaveChangesAsync` that calls `base.SaveChangesAsync`) and custom implementations of `IUnitOfWork` are excluded, because they implement saving and transactions.

## How to fix violations

Remove the call that saves changes or controls the transaction.

- `UnitOfWorkBehavior` saves the changes after the handler succeeds.
- When an explicit transaction is required before the handler runs (for example, for a row lock), implement `ITransactionalCommand` on the request.
- Implement cross-cutting processing that needs to control when changes are saved as an `IPipelineBehavior<TRequest, TResponse>`.

## Example

```csharp
public sealed class RenameShelfHandler(IShelfRepository shelves, IUnitOfWork unitOfWork) : IRequestHandler<RenameShelf, UuidV7>
{
    public async Task<UuidV7> HandleAsync(RenameShelf command, CancellationToken cancellationToken)
    {
        var shelf = await shelves.FindAsync(command.Id, cancellationToken) ?? throw new EntityNotFoundException(nameof(Shelf));
        shelf.Rename(command.Name);

        // Violates DFR0012
        await unitOfWork.SaveChangesAsync(cancellationToken);
        return shelf.Id;
    }
}
```

```csharp
public sealed class RenameShelfHandler(IShelfRepository shelves) : IRequestHandler<RenameShelf, UuidV7>
{
    public async Task<UuidV7> HandleAsync(RenameShelf command, CancellationToken cancellationToken)
    {
        var shelf = await shelves.FindAsync(command.Id, cancellationToken) ?? throw new EntityNotFoundException(nameof(Shelf));

        // Does not violate DFR0012: UnitOfWorkBehavior saves the changes
        shelf.Rename(command.Name);
        return shelf.Id;
    }
}
```

## When to suppress warnings

You can suppress the warning in processing that does not go through the request execution infrastructure (`IRequestExecutor<TRequest, TResponse>`), such as seeding initial data at application startup.

## Suppress a warning

If you just want to suppress a single violation, add preprocessor directives to your source file to disable and then re-enable the rule.

```csharp
#pragma warning disable DFR0012
// The code that's violating the rule is on this line.
#pragma warning restore DFR0012
```

To disable the rule for a file, folder, or project, set its severity to `none` in the [configuration file](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files).

```ini
[*.cs]
dotnet_diagnostic.DFR0012.severity = none
```
