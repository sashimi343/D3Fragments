# DFR0018: Use IIsolatedRequestExecutor to execute a command from a handler

| Property | Value |
|---|---|
| Rule ID | DFR0018 |
| Title | Use IIsolatedRequestExecutor to execute a command from a handler |
| Default severity | Warning |
| Fix is breaking or non-breaking | Non-breaking |
| Code fix | None |

## Cause

A constructor parameter of a command handler (an implementation of `IRequestHandler<TRequest, TResponse>` whose request implements `ICommand`) or a before-commit domain event handler (an implementation of `IBeforeCommitDomainEventHandler<TEvent>`) is an `IRequestExecutor<TRequest, TResponse>` that executes a command.

Note the following:

- The parameters of all instance constructors, including primary constructors, are checked.
- Classes that implement `IRequestExecutor<TRequest, TResponse>` (such as `RequestExecutor<TRequest, TResponse>`) are also reported. `IIsolatedRequestExecutor<TRequest, TResponse>` and its implementations are not reported.
- Executors of a query are not reported, because `UnitOfWorkBehavior` does not save the changes of a query.
- Executors whose request type is a type parameter are not reported, because whether the request is a command or a query cannot be determined.
- After-commit domain event handlers (implementations of `IAfterCommitDomainEventHandler<TEvent>`) are not reported. The commit has already completed, so they can execute another command in the same scope.
- When a query handler executes a command, [DFR0019](DFR0019.md) reports it instead of this rule.

This rule is checked only when `ArchitectureLayerAttribute` is set on the assembly.

## Rule description

`IRequestExecutor<TRequest, TResponse>` executes a command in the same dependency injection scope as the caller.
When a handler executes another command in the same scope, the two share the `DbContext`, so saving the inner command also saves the changes that the caller has not saved yet.
When the caller runs in a transaction (`ITransactionalCommand`), the transactions are nested and an exception is thrown.

To commit the changes of another command independently of the caller, use `IIsolatedRequestExecutor<TRequest, TResponse>`, which executes the request in a new dependency injection scope.
For details, see [Pipeline and transactions](../guide/04-application/02-pipeline-and-transactions.md#executing-a-command-in-a-separate-scope).

## How to fix violations

Change the type of the constructor parameter to `IIsolatedRequestExecutor<TRequest, TResponse>`.
To save the changes in the same transaction as the caller, do not execute another command. Write the processing in the handler, or use a domain event and a before-commit handler.

## Example

```csharp
public sealed class PlaceOrderCommandHandler(IRequestExecutor<RecordAuditCommand, Result> recordAudit)
    : IRequestHandler<PlaceOrderCommand, Result>
{
    // Violates DFR0018
}
```

```csharp
public sealed class PlaceOrderCommandHandler(IIsolatedRequestExecutor<RecordAuditCommand, Result> recordAudit)
    : IRequestHandler<PlaceOrderCommand, Result>
{
    // Does not violate DFR0018
}
```

## When to suppress warnings

Do not suppress a warning from this rule.

## Suppress a warning

If you just want to suppress a single violation, add preprocessor directives to your source file to disable and then re-enable the rule.

```csharp
#pragma warning disable DFR0018
// The code that's violating the rule is on this line.
#pragma warning restore DFR0018
```

To disable the rule for a file, folder, or project, set its severity to `none` in the [configuration file](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files).

```ini
[*.cs]
dotnet_diagnostic.DFR0018.severity = none
```
