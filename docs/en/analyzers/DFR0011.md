# DFR0011: Controllers should not inject domain classes through the constructor

| Property | Value |
|---|---|
| Rule ID | DFR0011 |
| Title | Controllers should not inject domain classes through the constructor |
| Default severity | Warning |
| Fix is breaking or non-breaking | Non-breaking |
| Code fix | None |

## Cause

A constructor parameter of a controller (a class whose module layer is `Presentation_Controller`) has a class or interface whose module layer is `Domain_Other` as its type.
For details on module layer names and how module layers are determined, see [Module layers](../architecture.md#module-layers).

Note the following points.

- The parameters of all instance constructors, including the primary constructor, are checked.
- Only a parameter whose type itself is `Domain_Other` is detected. Type arguments (for example, `IEnumerable<IPriceCalculator>`) are not checked.
- Using `Domain_Other` outside constructor parameters (parameters of action methods, local variables, member references, and so on) is not a violation.
- Only classes and interfaces in an assembly that has the domain layer only are determined as `Domain_Other`. Classes and interfaces in an assembly with multiple architecture layers are determined as `Other`, so this rule cannot detect them.

This rule is verified only when `ArchitectureLayerAttribute` is set on both the referencing and the referenced assemblies.

## Rule description

The responsibility of a controller is to receive an HTTP request and call the application layer (`IRequestExecutor<TRequest, TResponse>`).
When a controller injects and calls a domain class such as a domain service, the composition of domain logic leaks into the presentation layer, and the transaction control and pipeline behaviors of the application layer are bypassed.

In addition to domain services, `Domain_Other` includes classes derived from `TypeSafeEnum<TSelf, TKey>`, enums, error definitions, and so on.
Because these are legitimately used as DTO types or in branches, this rule detects only injection through DI (constructor parameters) instead of all references. A `Domain_Other` injected through DI can be regarded as a domain service.

Other references to the domain layer are verified by [DFR0002: Architecture reference violation (module reference)](DFR0002.md) (references to repository interfaces and domain rules, including constructor parameters, are detected by DFR0002).

## How to fix violations

Move the call to the domain service into a request handler, and call it from the controller through `IRequestExecutor<TRequest, TResponse>`.

## Example

```csharp
public class BooksController(IShippingFeeCalculator calculator) : ControllerBase
{
    // Violates DFR0011
    [HttpGet("{id}/shipping-fee")]
    public int GetShippingFee(UuidV7 id, int weight) => calculator.Calculate(weight);
}
```

```csharp
public class BooksController(IRequestExecutor<GetShippingFeeQuery, int> executor) : ControllerBase
{
    // Does not violate DFR0011
    [HttpGet("{id}/shipping-fee")]
    public Task<int> GetShippingFee(UuidV7 id, int weight, CancellationToken cancellationToken)
        => executor.ExecuteAsync(new GetShippingFeeQuery(id, weight), cancellationToken);
}
```

## When to suppress warnings

In general, do not suppress a warning from this rule.

You can suppress the warning if an assembly that has the domain layer only defines a class that is injected through DI but is not a domain service (such as a settings class placed in the domain layer).

## Suppress a warning

If you just want to suppress a single violation, add preprocessor directives to your source file to disable and then re-enable the rule.

```csharp
#pragma warning disable DFR0011
// The code that's violating the rule is on this line.
#pragma warning restore DFR0011
```

To disable the rule for a file, folder, or project, set its severity to `none` in the [configuration file](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files).

```ini
[*.cs]
dotnet_diagnostic.DFR0011.severity = none
```
