# DFR0002: Architecture reference violation (module reference)

| Property | Value |
|---|---|
| Rule ID | DFR0002 |
| Title | Architecture reference violation (module reference) |
| Default severity | Warning |
| Fix is breaking or non-breaking | Breaking (when changing the signature of a public member) / Non-breaking (when changing only the implementation) |
| Code fix | No |

## Cause

A dependency between modules (classes and interfaces) is inappropriate.
D3Fragments adopts an architecture based on Clean Architecture, but an inappropriate dependency is implemented where DFR0002 is reported.

Specifically, the following dependencies (references to and uses of classes and interfaces) are reported as violations. For details on module layer names and how module layers are determined, see [Module layers](../architecture.md#module-layers).

| Referencing module layer | Referenced module layer |
| :----------------------- | :---------------------- |
| Presentation_Controller  | Application_RequestHandler, Application_DomainEventHandler, Domain_RepositoryInterface, Infrastructure_* |
| Application_Request, Application_RequestHandler, Application_RequestExecutor, Application_DomainEventHandler | Presentation_Controller, Infrastructure_RepositoryImplementation |
| Domain_Entity, Domain_ValueObject | Application_Request, Application_RequestHandler, Application_RequestExecutor, Application_DomainEventHandler, Presentation_Controller, Domain_RepositoryInterface, Infrastructure_RepositoryImplementation |
| Domain_RepositoryInterface | Application_Request, Application_RequestHandler, Application_RequestExecutor, Application_DomainEventHandler, Presentation_Controller, Infrastructure_RepositoryImplementation |
| Domain_DomainRule        | Application_Request, Application_RequestHandler, Application_RequestExecutor, Application_DomainEventHandler, Presentation_Controller, Domain_RepositoryInterface, Infrastructure_RepositoryImplementation |

`Infrastructure_*` represents `Infrastructure_RepositoryImplementation` and `Infrastructure_Other`.

A violation occurs when the referenced class or interface is used in one of the following ways within the declaration of the referencing class or interface.

- Base class or implemented interface
- Type of a field, property, or event, and return type or parameter type of a method (including injection through constructor parameters)
- Type of a local variable, type in a type pattern or cast, and operand of `typeof`
- Type argument (for example, `List<IBookRepository>` or `IEnumerable<BookRepository>`)
- Invocation of or reference to a member (method, property, field, and so on), and instance creation
- Attribute

However, references inside `nameof` are not violations.

This rule is verified only when `ArchitectureLayerAttribute` is set on both the referencing and the referenced assemblies. References from or to an assembly without `ArchitectureLayerAttribute` are always allowed.

If the module layer of either the referencing or the referenced side is `*_Other` or `Other` (an other class whose architecture layer cannot be identified in an assembly with multiple architecture layers), the reference is not a violation unless it is listed in the table above.
For example, in a domain + application layer assembly, this rule cannot detect an entity that references a helper class of the application layer (a class determined as `Other`).

## Rule description

D3Fragments adopts an architecture based on Clean Architecture.
Clean Architecture defines rules for dependencies between layers.
To keep the system maintainable, it is recommended to comply with the dependency rules between layers.

Dependencies at the assembly (project) level are verified by [DFR0001: Architecture reference violation (project reference)](DFR0001.md).
This rule verifies dependencies at a finer granularity that cannot be covered by the assembly-level verification.
Dependencies across architecture layers within an assembly with multiple architecture layers are also verified by this rule.

References from `Domain_DomainRule` (implementations of `IDomainRule<TContext>`) to repository interfaces are forbidden to keep domain rules as pure checks that do not depend on external I/O. Retrieve the data required for the check from the repository in the caller and pass it as `TContext`.

## How to fix violations

To fix a violation of this rule, remove the reference to the class or interface that is not allowed.

For example, if a controller uses a request handler or a repository directly, call the application layer through `IRequestExecutor<TRequest, TResponse>`.

## Example

```csharp
public class BooksController(IBookshelfRepository repository) : ControllerBase
{
    // Violates DFR0002: Presentation_Controller references Domain_RepositoryInterface
    [HttpGet("{id}")]
    public async Task<IActionResult> Get(UuidV7 id, CancellationToken cancellationToken)
        => Ok(await repository.FindAsync(id, cancellationToken));
}
```

```csharp
public class BooksController(IRequestExecutor<GetBookshelfQuery, BookshelfDto> executor) : ControllerBase
{
    // Does not violate DFR0002
    [HttpGet("{id}")]
    public async Task<IActionResult> Get(UuidV7 id, CancellationToken cancellationToken)
        => Ok(await executor.ExecuteAsync(new GetBookshelfQuery(id), cancellationToken));
}
```

## When to suppress warnings

In general, do not suppress a warning from this rule.

## Suppress a warning

If you just want to suppress a single violation, add preprocessor directives to your source file to disable and then re-enable the rule.

```csharp
#pragma warning disable DFR0002
// The code that's violating the rule is on this line.
#pragma warning restore DFR0002
```

To disable the rule for a file, folder, or project, set its severity to `none` in the [configuration file](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files).

```ini
[*.cs]
dotnet_diagnostic.DFR0002.severity = none
```
