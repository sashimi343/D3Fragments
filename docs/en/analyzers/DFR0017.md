# DFR0017: Do not call SignInManager methods that write to the database and the cookies together

| Property | Value |
|---|---|
| Rule ID | DFR0017 |
| Title | Do not call SignInManager methods that write to the database and the cookies together |
| Default severity | Warning |
| Fix is breaking or non-breaking | Non-breaking |
| Code fix | None |

## Cause

One of the following methods of ASP.NET Core Identity's `SignInManager<TUser>` (or a class derived from it) is called.

| Method | Use instead |
|---|---|
| `PasswordSignInAsync` | `VerifyPasswordAsync`, `CompleteSignInAsync` / `BeginTwoFactorSignInAsync` |
| `CheckPasswordSignInAsync` | `VerifyPasswordAsync` |
| `TwoFactorSignInAsync`, `TwoFactorAuthenticatorSignInAsync` | `VerifyTwoFactorCodeAsync`, `CompleteTwoFactorSignInAsync` |
| `TwoFactorRecoveryCodeSignInAsync` | `VerifyRecoveryCodeAsync`, `CompleteTwoFactorSignInAsync` |
| `PasskeySignInAsync` | `PerformPasskeyAssertionAsync`, `VerifyPasskeyAsync`, `CompleteSignInAsync` |
| `ExternalLoginSignInAsync` | `VerifyExternalLoginAsync`, `CompleteSignInAsync` / `BeginTwoFactorSignInAsync` |

`Verify*` are extension methods of `Sashimi343.D3Fragments.Identity.EFCore`, and `Complete*` and `BeginTwoFactorSignInAsync` are extension methods of `Sashimi343.D3Fragments.AspNetCore` (namespace `D3Fragments.AspNetCore.Identity`).

Calls inside a class derived from `SignInManager<TUser>` (such as an override that calls the `base` method) are not checked, because that class implements the methods.
This rule is verified only when `ArchitectureLayerAttribute` is set on the calling assembly.

## Rule description

Each of these methods does the following two things in one call.

- Writes to the database: increments and resets the access failed count, locks the user out, redeems recovery codes, and updates passkey data
- Operates on cookies: the application cookie, the cookie of the user waiting for two-factor authentication, and the "remember this browser" cookie

In D3Fragments, database writes are done inside a command, and `UnitOfWorkBehavior` saves them together with the domain changes.
Issuing a cookie, on the other hand, is an HTTP concern and is done in the presentation layer.
These methods cause problems whichever layer calls them.

- Called from the presentation layer: with stores that leave saving to the unit of work (`AddD3FragmentsStores`), the database changes are not saved, so the access failed count is not recorded and lockout does not work
- Called inside a command: the cookie is issued before the changes are committed, and the application layer depends on HTTP

`CheckPasswordSignInAsync` also needs an HttpContext for a user with two-factor authentication enabled, because it reads the "remember this browser" cookie.

## How to fix violations

Perform the database side inside a command with the `Verify*` extension methods, and after the command succeeds, call the cookie-side extension methods in the presentation layer.
The `Verify*` extension methods follow the same steps as the corresponding `SignInManager<TUser>` methods and return the same `SignInResult`.
Return a failed sign-in as a result, not as an exception (when a command throws, the unit of work discards the changes and the access failed count is not saved).
The user type (`Account` in the example below, derived from `IdentityUser<TKey>`) belongs to the infrastructure layer. The presentation layer may reference it to call the cookie-side extension methods ([DFR0002](DFR0002.md) allows it).

## Example

```csharp
public sealed class LoginController(SignInManager<Account> signInManager, UserManager<Account> userManager) : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> LoginAsync(LoginRequest request)
    {
        var account = await userManager.FindByNameAsync(request.UserName);

        // Violates DFR0017
        var result = await signInManager.PasswordSignInAsync(account!, request.Password, false, lockoutOnFailure: true);
        return result.Succeeded ? Ok() : Unauthorized();
    }
}
```

```csharp
// Application layer: an interface that the application defines
public interface IAuthenticationService
{
    Task<LoginOutcome> CheckPasswordAsync(string userName, string password, string? rememberedUserId, CancellationToken cancellationToken);
}

// Infrastructure layer: the implementation (called inside a command; UnitOfWorkBehavior saves the changes)
internal sealed class IdentityAuthenticationService(SignInManager<Account> signInManager) : IAuthenticationService
{
    public async Task<LoginOutcome> CheckPasswordAsync(string userName, string password, string? rememberedUserId, CancellationToken cancellationToken)
    {
        var account = await signInManager.UserManager.FindByNameAsync(userName);
        if (account is null)
        {
            return LoginOutcome.Failed;
        }

        // Does not violate DFR0017: only the database side is performed
        var result = await signInManager.VerifyPasswordAsync(account, password, lockoutOnFailure: true, rememberedUserId == account.Id.ToString());
        return LoginOutcome.From(result, account.Id);
    }
}

// Presentation layer
public sealed class LoginController(IRequestExecutor<Login, LoginOutcome> login, SignInManager<Account> signInManager) : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> LoginAsync(LoginRequest request, CancellationToken cancellationToken)
    {
        var rememberedUserId = await signInManager.GetTwoFactorClientRememberedUserIdAsync();
        var outcome = await login.ExecuteAsync(new Login(request.UserName, request.Password, rememberedUserId), cancellationToken);

        // Does not violate DFR0017: only the cookie side is performed after the command succeeds
        var account = await signInManager.UserManager.FindByIdAsync(outcome.AccountId.ToString());
        if (outcome.Succeeded)
        {
            await signInManager.CompleteSignInAsync(account!, isPersistent: false);
        }
        else if (outcome.RequiresTwoFactor)
        {
            await signInManager.BeginTwoFactorSignInAsync(account!);
        }
        return outcome.Succeeded || outcome.RequiresTwoFactor ? Ok(outcome) : Unauthorized();
    }
}
```

## When to suppress warnings

You can suppress the warning in an application that does not use stores that leave saving to the unit of work, and does not change or check the domain on sign-in.

## Suppress a warning

If you just want to suppress a single violation, add preprocessor directives to your source file to disable and then re-enable the rule.

```csharp
#pragma warning disable DFR0017
// The code that's violating the rule is on this line.
#pragma warning restore DFR0017
```

To disable the rule for a file, folder, or project, set its severity to `none` in the [configuration file](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files).

```ini
[*.cs]
dotnet_diagnostic.DFR0017.severity = none
```
