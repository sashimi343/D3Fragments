# DFR0010: Value objects should not have public setters

| Property | Value |
|---|---|
| Rule ID | DFR0010 |
| Title | Value objects should not have public setters |
| Default severity | Warning |
| Fix is breaking or non-breaking | Breaking |
| Code fix | Yes (properties only) |

## Cause

A type (class, struct, or record) that directly or indirectly inherits the `D3Fragments.ValueObjectBase<TSelf, TPrimitive>` class, or directly or indirectly implements the `D3Fragments.IValueObject<TSelf, TPrimitive>` interface, declares one of the following members.

- A property that has a `set` accessor or an `init` accessor whose accessibility is `public`, `internal`, or `protected internal`
- A field whose accessibility is `public`, `internal`, or `protected internal` and that is not `readonly` (excluding `const`)

The accessibility of accessors, excluded members, and where violations are reported are handled in the same way as [DFR0003](DFR0003.md).
Properties generated from the parameters of a positional record have `init` accessors, so they are violations.

This rule is verified regardless of the architecture layer setting of the assembly (`ArchitectureLayerAttribute`).

## Rule description

Value objects should be immutable.
If the value of a value object can be changed after it is created, the state of other objects that share the value object also changes unintentionally.
In addition, invalid values can be set without going through the validation performed by factory methods such as `Create`.

## How to fix violations

Remove the setter to make the property get-only, or change the accessibility of the setter to `private`. For fields, make them `readonly`.
To change a value, create a new value object.

The code fix changes the setter (`set` / `init`) of the property to `private set`.

## Example

```csharp
public sealed class Email : ValueObjectBase<Email, string>, IValueObject<Email, string>
{
    // Violates DFR0010
    public string Domain { get; set; }

    ...
}
```

```csharp
public sealed class Email : ValueObjectBase<Email, string>, IValueObject<Email, string>
{
    // Does not violate DFR0010
    public string Domain { get; }

    ...
}
```

## When to suppress warnings

In general, do not suppress a warning from this rule.

## Suppress a warning

If you just want to suppress a single violation, add preprocessor directives to your source file to disable and then re-enable the rule.

```csharp
#pragma warning disable DFR0010
// The code that's violating the rule is on this line.
#pragma warning restore DFR0010
```

To disable the rule for a file, folder, or project, set its severity to `none` in the [configuration file](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files).

```ini
[*.cs]
dotnet_diagnostic.DFR0010.severity = none
```
